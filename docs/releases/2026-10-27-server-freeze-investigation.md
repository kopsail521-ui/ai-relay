## 源码及本地复现

1. **大文件在多个服务中完整复制，没有全局在途字节预算。** moderation 通用请求可到 128MiB、上传 100MiB，再转媒体服务重新缓冲。仅 32MiB 正文的两层缓冲实验就观察到约 96MiB Buffer 占用，尚不含 base64/JSON 等副本。少数同时上传的用户也能消耗明显内存，不能用低日活排除压力。未证明发生过生产 OOM。
2. **图片任务没有后台总寿命/并发上限。** `image-service.mjs` 的后台循环在 processing、404 或持续查询失败时不会自然停止；180 秒只约束 HTTP 等待。真实类加本地假处理服务验证，请求闭包在轮询阶段仍可能持有参考图。生产两个陈旧 running 任务与缺少生命周期管理相符；尚不能证明当前有大量累积或内存泄漏导致整站故障。
3. **SQLite 等锁会阻塞 native 的 Node 事件循环。** `ImageLedger.transaction()` 使用同步 `BEGIN IMMEDIATE` 和 5 秒 busy timeout，读操作也通过事务执行。另一进程持锁 500ms 的临时数据库复现中，账本操作阻塞约 535ms，10ms 定时器延至约 537ms。能够造成该服务的健康检查/查询一同变慢，不能单独推导为 Caddy 或整机卡死。
4. **native 非图片上传中断存在未捕获异常。** 在读取正文的 `await readBody(req)` 外没有错误边界；本地真实 HTTP + 临时钱包中，发送部分正文后断开导致 Node 22 以 ECONNRESET/aborted 退出，处理端收到请求数为 0。此前 Gitee 已修，native 仍有遗漏。本轮未部署此修复；当前 native 重启次数为 0，不能称它已触发生产故障。
5. **发布/日志容量没有长期保留策略。** native/gitee 每次发布保留独立停止容器与镜像，`docker image prune -af` 不会删除被停止容器引用的镜像。safe-pull 的博客临时备份成功后不清理；New API 同时输出文件日志且无历史删除策略。控制台/proxy 重建脚本未保留资源/日志限制，后续发布可能覆盖手工配置。

仓库未发现定时重启/定时清理工作流；常规发布使用共享 VPS 互斥锁，不能声称多个 CI 同时编译导致卡顿。控制台 Go/Bun 编译在 GitHub runner，媒体镜像仍在 VPS 构建。代码性能中间件默认在资源超过 90% 时返回 503，但只影响接入 API，不足以解释首页 TCP 不可达。

## 处理优先级

- 先补齐上传错误边界、后台轮询生命周期/并发和大文件在途内存预算，保留既有任务 ID、幂等与计费语义，避免通过超时盲目重提生成任务。
- 按现有容器真实配置保参加入日志轮转；修复部署脚本避免下次发布丢配置。保留有限个可回滚版本，按精确容器身份清理过期备份；不能用无差别 prune 删除用户数据或唯一恢复点。
- 在维护流程中保留短周期资源与健康状态的有限历史，下一次失联先区分公网入口、Caddy、3000、3001 和媒体服务，并记录 HTTP 状态或连接失败及 memory/io PSI。此次仅新增手动只读采集器，没有安装定时器、重启守护或自动清理。
- 现有 1GB 档主机的空闲预算不适合无约束的大文件并发；增加内存可增加余量，但不能替代修复任务/日志/部署增长问题，也不能据此保证不再失联。本轮没有改套餐或购买资源。
