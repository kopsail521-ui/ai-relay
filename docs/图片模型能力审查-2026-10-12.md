# KeyoAPI 图片模型能力审查

审查日期：2026-10-12。内部技术报告，不用于公开网站或市场文案。

## 结论与证据边界

以下缺陷与行号记录修复前的审查快照，不代表当前本地源码仍存在这些问题。当前本地修复及验证进度见文末“本地修复状态”；生产版本尚未比对或部署。审查时网关没有完整暴露已配置图片模型的能力，已确认的主要缺口包括：Nano Banana 原生分辨率字段丢失、base64 参考图被过滤、multipart edits 被审核代理拒绝、GPT 透明背景和蒙版被丢弃、参考图转发异常后退回另一条接口、尚在运行的任务被重复提交、张数与输出格式被静默忽略。它们不能都归因于客户写错尺寸。

本次核对线上库存、实际供应商公开契约、当前本地实现与客户文档，并用实际源码片段进行隔离模拟。共覆盖 9 个生图模型、6 个图像处理/视觉模型、2 个图像审核模型。未发起付费生图、修改生产选项/余额、部署、提交或推送代码。新增文件仅为内部报告与本地诊断证据。

重要边界：本地模拟证明参数处理和任务控制的代码行为，不证明供应商接受模拟参数，也不是每个模型的线上生成验收。本地源码与生产容器内容仍需部署版本证据作精确比对。Grok 实际供应商契约未取得；第二条 .5 高端型号渠道的文档已失效；上传有效鉴权写入及其 503 根因未验证。

之前线上确认的结果仍然有效：`gpt-image-2-vip` 经公网网关，使用 HTTPS 参考图与 `size: "3840x2160"`，返回真实 3840×2160 PNG，未做超分。该结果只覆盖这一条请求，不能推出全部图片模型、输入格式和编辑能力均可用。

## 客户截图的含义

截图通过本地 OCR 提取，未依赖视觉判断。可可靠辨认的意思是：公开 HTTPS 参考图通过 `images` 和 `/v1/images/generations` 可以使用；此前 base64 与 `/v1/images/edits` 的尝试不能据此判断模型不理解参考图；可优上传入口当时返回 503，因此尚未证明本地画布图片通过可优上传再生成的完整流程。

部分接口名称、哈希内容不能可靠识别。截图不能证明输出的角色相似程度、尺寸或具体模型。

2026-10-12 08:20–08:22 UTC 的当前检查：

- `/v1/uploads` 与 `/v1/files` 无鉴权返回明确 401。
- 保存的现有诊断 relay key 在 `/api/usage/token/` 与上传请求均返回无效 token/key 的 401，没有执行图片写入。
- 公开品牌 PNG 返回 200，验证了静态文件读取；这不验证上传目录写入。
- 已有管理 token 能读取管理日志。最近 48 小时 25 条管理错误、七天最近 100 条错误均未找到上传故障；上传代理在 new-api 之前处理，缺少这些记录不能否定客户 503。
- 无可用生产 SSH 配置或身份，未读取生产上传目录权限、挂载、剩余空间与代理 stderr。

因此，当前不能宣称上传已恢复，也不能确定为磁盘满或权限问题。源码中 `storage_insufficient` 对应空间不足/ENOSPC/EDQUOT；`storage_unavailable` 对应其他文件系统异常。必须有客户那次完整错误体或代理日志，才能定位。证据：`services/creem-moderation-proxy/server.mjs:978`。图像生成审核另有 `moderation_unavailable` 503，应按路径和 code 区分。

## 生图模型逐项能力

共同原生协议：`POST /v1/api/generate`，`model`、`prompt` 必填；`images: string[]` 支持 URL 与 base64；`replyType` 为 json/stream/async；异步查询 `GET /v1/api/result?id=...`。

| 当前模型 | 实际供应商文档能力 | 当前实现主要缺口 |
|---|---|---|
| gpt-image-2 | 比例或 1K 像素值；quality=auto；共用 schema 有 mask URL | base64、mask 丢失；没有完整型号参数校验；请求张数/格式静默忽略 |
| gpt-image-2-vip | 1–4K 像素值；quality=medium；transparent；mask URL | HTTPS 参考+3840×2160 已有线上成功；base64、background、mask 未接全；错误质量仍会发送 |
| gpt-image-2.5 | 比例或 1K 像素值；quality=auto；共用 schema 有 mask URL | 同基础型号；线上端点元数据只广告 chat，客户入口信息不完整 |
| gpt-image-2.5-flare | 1–4K 像素值；low/medium/high；transparent；mask URL | background/mask/base64 丢失；尺寸验证正则不匹配实际 ID；兼容路径绑定两个等优先级渠道 |
| gpt-image-2.5-sunburst | 1–4K 像素值；low/medium/high/xhigh/max；transparent；mask URL | 同 flare；质量差异未形成型号规则；两个渠道契约未统一验证 |
| nano-banana-2 | aspectRatio 比例 + imageSize=1K/2K/4K；URL/base64 参考 | imageSize 丢失；像素 size 被误送给 aspectRatio；base64 被过滤 |
| nano-banana-2.1 | 明确在原生型号清单；共同的比例/imageSize schema | 同上；旧 config/grsai.json 没有这一型号，配置来源不一致 |
| nano-banana-pro | aspectRatio 比例 + imageSize=1K/2K/4K；URL/base64 参考 | 同其他 Nano；不能按 GPT 像素参数模板保证原生 4K |
| grok-image-2.0 | 当前配置证明 chat 路由及供应商别名映射；未取得实际契约 | 参考图/尺寸/质量/多张/格式/异步均未核实；不能套用原厂直连接口假定 |

型号级尺寸细节：

- GPT 基础与 2.5 文档明确只支持 1K 像素或比例，不能把高端型号原生 4K 推广到所有 GPT 图片模型。具体基础比例像素表只标 gpt-image-2，不能把它逐项作为 2.5 的保证。
- VIP/flare/sunburst 文档共享推荐像素表：16:9 高档为 3840×2160，正方形高档为 2880×2880。高端型号不接受 `16:9` 比例字符串，应使用像素值。
- 自定义四项限制的原文明确为“仅限 vip 模型”：最长边≤3840，两边为16倍数，长短边比≤3:1，655,360–8,294,400总像素。不能直接把同一验证器复制到 flare/sunburst 并声称文档已保证这些限制。
- Nano 比例列表是 auto、1:1、16:9、9:16、4:3、3:4、3:2、2:3、5:4、4:5、21:9。“nano-banana-2系列”另列1:4、4:1、1:8、8:1；2.1是否包括在额外比例中没有单独解释。
- Nano schema 未列 quality/background/mask。GPT schema 的 mask 是 URL 字符串，没有逐型号说明。参数应按支持范围处理，未知能力不能默默假定。
- 原生 schema 未列 n/response_format；响应 results 是数组并不证明可以请求任意张数。若网关提供兼容功能，必须自己实现并说明计费，或明确拒绝不支持值。

线上路由观察：前八个型号绑定主图片渠道。flare/sunburst 还绑定另一渠道，两渠道 priority=0、weight=1，为同一候选池，不是有序主备；带参考图的原生分支却固定使用主来源。纯文本与参考图请求可能因此走不同契约。Grok 为另一渠道且映射 `grok-image-2.0 → grok-图片-2.0`。以上属于管理 API 的脱敏配置观察，不是各渠道逐型号生成测试。

## 图像工具和审核模型

这些是独立工具能力。AnimeSharp/Real-ESRGAN 专用放大不应替代生图模型的原生分辨率。

| 当前模型 | 文档接口 | 输入及关键输出 | 审查状态 |
|---|---|---|---|
| VajraV1 | /v1/images/object-detection、segmentation、pose-detection | multipart URL或文件二选一；bbox、分割mask、姿态关键点 | 专用转发保留原始请求；未做付费操作验收 |
| sam3 | /v1/images/object-detection、segmentation | multipart URL或文件；检测/分割；无pose接口 | 同上 |
| AnimeSharp | /v1/images/upscaling | multipart URL或文件；response_format=url/b64_json | 无scale、目标size、quality、n参数证据；未做操作验收 |
| Real-ESRGAN | /v1/images/upscaling | 同上 | 同上 |
| UVDoc | /v1/images/unwarping | multipart URL或文件；url/b64_json | 专用转发保留请求；未做操作验收 |
| RMBG-2.0 | /v1/images/mattings | multipart URL或文件；url/b64_json | 实际目录是抠图，线上端点元数据误标upscaling |
| nsfw-classifier | /v1/moderations | JSON多模态input；image_url.url支持URL或Base64；flagged/categories/category_scores | 模型列在文档enum；未做实际审核验收 |
| nonescape-v0 | /v1/moderations | 同共用schema；图片真伪/AI生成检测用途 | 文档没有逐模型模态细则；未做实际审核验收 |

图像工具没有文档化的 base64 输入；`b64_json` 是输出格式。工具接口没有 async 参数。object-detection 另外列出 prompt、caption_level；这些不应被通用生图参数覆盖。Gitee 文档还列 SeedVR2-3B、Florence-2-large，但不在当前已配置图片工具清单。

## 已复现或源码确认的缺陷

### 1. 编辑入口被审核代理阻断

`services/creem-moderation-proxy/server.mjs:1430` 对 generations/edits/variations 一律 JSON.parse。`multipart/form-data` edits 因此立即400 Invalid JSON body，尚未到 new-api 的现有编辑适配器。上游兼容 edits 自身就写 multipart；其中 image 字段示例为URL字符串，没有 binary格式说明。网关支持本地二进制编辑时需要额外适配，不能把现有new-api multipart能力等同实际供应商可接收二进制。

### 2. 参考图格式及字段缺失

`services/apimart-passthrough/server.mjs:779` 只保留HTTP(S)，过滤上游明确支持的base64；singular `image: [...]` 没有遍历；静默去重并截断9张，文档没有9图上限。混合有效/无效输入没有逐项报错。源码执行模拟复现了base64和singular数组400。

### 3. Native请求未完整转发能力

`services/apimart-passthrough/server.mjs:836` 将size优先映射aspectRatio，覆盖独立比例选择；`:896` 构造native只含model/prompt/images/replyType/aspectRatio/quality。全部八个型号模拟请求均丢background/mask，三个Nano均丢imageSize。resolution别名未处理。应按模型区别像素与比例+档位。

### 4. 校验不能证明全型号正确

`:843` 的正则只匹配实际清单中的VIP，不匹配`.5-flare/.5-sunburst`。更基本的问题是没有完整型号尺寸和质量规则：mock中基础1K型号仍转发3840×2160、VIP仍转发quality=high。mock的成功响应只是隔离测试桩，不代表上游接受。VIP对不符合像素正则的比例/拼写也未完整拒绝。修复应使用已证实的逐型号规则与明确错误。

### 5. n与返回格式静默忽略

`:1003` 的n只对返回URL数组slice，不产生多个任务。模拟n=3仍只得1张，response_format=b64_json仍返回url。未文档化的参数应明确拒绝或实现，不应把成功HTTP当作已满足要求。

### 6. 原生转发失败后切换契约

`services/creem-moderation-proxy/server.mjs:1493` 的catch同时覆盖解析与native transport异常，异常后继续普通new-api转发。mock确实复现native传输异常后兼容路径返回200。参考字段可能丢失；若原生任务已经创建而响应丢失，还可能出现双提交。需要保留相同请求语义并报告明确错误。

### 7. 重试会重复运行中或被拒绝的任务

`services/apimart-passthrough/server.mjs:972` 每轮最长100秒，但`:947`下一轮无条件提交新任务。上一任务还running时也会再提交；模拟复现两次提交后504及退款。无URL的completed也会再次提交。taskStatus将violation映射failed，`:1009`随后重新提交；本地模拟复现内容拒绝被重试。内容拒绝应是终态，不能通过再次提交绕过。源码关于失败集中于某队列的注释没有供应商证据。

### 8. 异步能力、追踪和恢复不足

强制replyType=async但最终同步等待，没有对外暴露stream/async选择。图片任务没有持久化和可靠恢复；总期限在首次提交完成之后起算，fetch无明确abort期限；进程重启、连接中断、超时退款后仍运行的任务缺少一致状态与结算。不是每个最终错误都带task ID，原始上游错误也可能暴露内部来源信息。应以任务ID持久记录、单任务持续轮询、终态结算及受控错误输出为基础。

### 9. 权限与计费未与主网关一致

`services/apimart-passthrough/server.mjs:157` DB lookup读取status但没有expiry、模型限制、IP/分组限制与用户状态；有大小写不敏感/trim/fallback匹配。`:398`只检查用户quota，未在扣费前检查token remain_quota；DB不可写`:403`返回skipped成功；probe有效但本地不识别`:239`设置skipBill。native售价是catalog固定快照，未保证线上ModelPrice/分组定价一致。`:245`日志channel搜索video/APIMart而非实际图片渠道。这里是源码审查，未进行生产权限绕过或余额试验。

Gitee工具透传也直接读取DB并手动扣费，具有类似的token限制及token余额边界缺口。证据：`services/gitee-passthrough/server.mjs:151`、`:199`、`:286`。该服务`:653`、`:987`原样转发请求、完整缓冲响应、按调用扣费，没有实际SSE流转发。工具本身没有文档化stream参数，因此不应把缺SSE一律当作这些工具合同缺陷。应统一鉴权和结算，避免为每个图片路径维护不一致逻辑。

### 10. 普通兼容路径同样存在字段边界

`new-api/relaykit/dto/openai_image.go:74` 将JSON未知图片字段收集到Extra，自定义序列化未合并Extra。正常解析/重编码的type-1图片路径会丢imageSize、resolution及未定义参考字段等。Chat DTO在`new-api/relaykit/dto/openai_request.go:44`没有同类未知字段保留器，顶层图片控制字段同样无保证；chat的response_format是对象而不是Images API字符串。若启用raw-body passthrough可能改变这些行为，当前全局开关未核实，不能把源码默认行为无条件宣称为每个生产请求的行为。

已有OpenAI multipart edits适配器在`new-api/relay/channel/openai/adaptor.go:450`、`:537`保留非model文本字段、image文件及首个mask；当前前置审核代理先400，因此存在代码支持不等于公网可达能力。供应商edits schema仍只保证URL字符串，需要与二进制输入做适配。

标准图片审核输入保留：`new-api/relaykit/dto/openai_request.go:45`的Input any保留`input: [{type:"image_url", image_url:{url:"..."}}]`中的嵌套对象，type-1转换/Marshal没有清除该字段。只有顶层image_url而无input会先因缺input被拒绝（`new-api/relay/helper/valid_request.go:358`）；顶层字段本身不在DTO。不应误称所有审核图片都被丢弃。以上为静态证据，未做实际审核请求。

## 客户文档与元数据问题

- `:315`“九成是size不在上表”没有统计或根因证据，英文“almost always”同样不成立。正确尺寸的上游请求也发生过失败。

- `docs/客户接入一页纸.md:105`仍声称参考图决定输出尺寸，与请求尺寸可独立生效的事实冲突。
- `static/brand/keyo-docs.html` 缺完整参考图、型号尺寸/质量及Nano原生分辨率说明。

## 修复范围与验收要求

本节保留首次审查提出的验收范围。后续本地修复已覆盖其中部分项目，详情见文末；线上验证仍未执行。按客户影响，验收范围包含：

1. 上传：先取得有效key的微小PNG上传+公开读回，以及完整503 code/代理日志；据此处理具体挂载、权限、空间或服务问题。验证路径覆盖/v1/uploads与/v1/files，401探测不能替代。
2. 统一生图与编辑能力：为八个原生型号分别定义字段/尺寸/quality，完整转发受支持的base64、background、mask、Nano imageSize；正确解析multipart并适配供应商接受格式；同一路径支持文生图和参考图，不发生语义静默回退。
3. 任务处理：持久化task ID；running持续查询同一任务；内容拒绝终止；明确业务失败、轮询传输错误、提交结果不明；超时不丢任务；确保结算/退款一次且可追溯。
4. 兼容参数：对n、response_format、stream/async等明确实现或拒绝；若下载转换b64输出，须明确限制和失败行为。不得用超分假冒原生4K。
5. 权限计费：执行与new-api一致的token过期/型号/IP/组/用户限制及用户和token额度检查；数据库不可用不得漏收费；价格来源与线上选项一致，渠道日志正确。
6. 路由与说明：核实所有活跃供应商契约后配置同能力路由；更新RMBG端点以及网站HTML、两种Markdown、一页纸，逐型号说明能力。

修复后的决定性验收应从源码字段保留测试和不付费mock开始，再有控制地验证实际供应商与公网网关：八个原生型号分别至少有文本/参考输入的契约证据；高档GPT和三个Nano检查实际输出像素与请求比例；透明背景检查alpha而非视觉猜测；蒙版检查编辑区域；本地文件/base64/URL各走完整链；工具检测/分割/姿态/抠图/矫正/放大按自己的端点检查；不支持值明确400；超时仍查询同task ID；内容拒绝只提交一次；限制token与余额边界按隔离测试确认。若未执行某项实际验证，应标为未验证，不能宣布所有型号充分可用。
